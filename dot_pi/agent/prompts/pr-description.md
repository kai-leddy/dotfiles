---
description: Generate a PR description for the current branch (Jira context + diff + repo template)
argument-hint: "[base-branch]"
---
Generate a pull request description for the current branch by combining the Jira ticket context, the git diff of meaningful files, and the repository's PR template.

## Workflow

### 1. Establish the merge base

```bash
git branch --show-current              # current branch name
git merge-base ${1:-master} HEAD       # base branch defaults to master, override with an argument
```

Store the merge base SHA for all subsequent diff commands.

### 2. Extract Jira ticket from branch name

Match `[A-Z]+-\d+` against the branch name. If found, proceed to step 3. If not found, skip Jira steps and continue gracefully - omit the Jira line from the PR description.

### 3. Fetch Jira context

```bash
acli jira workitem view <TICKET> --fields summary,description,status
```

Use the returned summary and description to understand the _problem being solved_ - this informs the PR description's framing.
The link to the Jira ticket can be derived by using `acli jira auth status` to get the domain name for the Jira site and appending `/browse/<TICKET>`.

If `acli` is unavailable or the command fails, skip silently and continue.

### 4. Fetch existing PR description (if updating an existing draft)

```bash
gh pr view --json body --jq .body
```

Use the above GH CLI command to view any existing PR description if the current branch already has an open PR. This allows the user to update an existing description rather than always generating a new one from scratch. If no existing PR or description is found, proceed with generating a new one.

### 5. Classify files to exclude

Run `git diff --stat <merge_base>..HEAD` to get the full file list and line counts without fetching any content.

Classify each file. Exclude a file if **any** of the following apply:

**Universal exclusions**

- Lockfiles: `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `Gemfile.lock`, `poetry.lock`, `Cargo.lock`, `go.sum`, `*.lock`
- Sourcemaps: `*.js.map`, `*.css.map`
- Minified files: `*.min.js`, `*.min.css`
- Type declaration files: `*.d.ts`, `*.tsbuildinfo`
- Build artifacts / compiled output: `dist/`, `build/`, `out/`, `*.pyc`, `__pycache__/`
- Binary files (images, fonts, archives): `*.png`, `*.jpg`, `*.gif`, `*.svg`, `*.woff`, `*.woff2`, `*.ttf`, `*.zip`, `*.tar.gz`

**Vendored / third-party code**

- `vendor/`, `node_modules/`, `Pods/`, `third_party/`, `extern/`

**Codegen - repo-specific signals (check these)**

- `.gitattributes`: any file listed with `linguist-generated=true`
- Generated file headers: run `head -5 <file>` on any file that looks potentially generated (e.g. lives under `gen/`, `generated/`, `__generated__/`, `.gen/`, or has an extension like `.pb.go`, `.pb.ts`, `.graphql` if schema-generated). Exclude if the header contains markers like `# Code generated`, `// @generated`, `/* auto-generated */`, `DO NOT EDIT`, `// Generated by`, etc.
- Common codegen directories: `gen/`, `generated/`, `__generated__/`, `.gen/`, `migrations/` (if auto-generated)

When in doubt about a file, include it - it is better to have slightly more context than to miss a meaningful change.

### 6. Build and execute the diff

Craft a **single** `git diff` command using `:(exclude)` pathspecs for every file classified for exclusion:

```bash
git diff --unified=0 --abbrev=1 --no-prefix <merge_base>..HEAD \
  ':(exclude)path/to/lockfile' \
  ':(exclude)path/to/generated.go' \
  # ... one entry per excluded file
```

### 7. Find the PR template

Check in order:

1. `pull_request_template.md` at the repo root (alongside the `.git` folder)
2. `.github/pull_request_template.md`
3. `.gitlab/merge_request_templates/Default.md` (or any default in `.gitlab/`)

If found, use that file's format as the output structure. If none found, use this fallback template:

```markdown
**Jira**: [TICKET-123](JIRA_URL)

## Description

{{ One or two sentences giving a high-level description of the PR and its purpose. Mention all major changes, but keep it short and concise. Omit this section's Jira line entirely if no ticket was found. }}

**List of changes**

- {{ Bullet point list of each high-level change made. No trailing periods. }}

## Steps to Test

{{ Numbered list of steps required to test the changes. Keep it simple. If it is unclear how the PR should be tested, use the notice block below instead: }}

> [!NOTE]
> Testing steps unclear - reviewer please advise.

## Supporting Resources

> [!IMPORTANT]
> Add links to any documentation here, or delete this section if not required.

## Dev Complete Checklist

- [ ] {{ If any TODO comments are visible in the diff, add a checklist item for each one here. Otherwise omit. }}
```

### 8. Generate the PR description

Using the collected context (Jira summary + description, branch name, git diff, PR template), write the PR description.

**Tone rules - apply throughout:**

- British English spelling (e.g. "behaviour", "initialise", "colour")
- Voice: lazy lead software developer - informed, direct, no corporate fluff
- Informal but professional - do not say things like "Right then", "let's crack on", or "sort this out"
- No trailing periods on bullet list items
- Output **raw Markdown only** - no code block wrapper, no preamble, no explanation

**Content rules:**

- Description: 1-2 sentences, high-level, covers all major changes without padding
- List of changes: high-level bullet points - not a line-by-line diff summary
- Steps to test: simple, actionable; use the `[!NOTE]` notice if testing approach is genuinely unclear
- If any TODO comments appear in the diff, add a checklist item for each in the Dev Complete Checklist
- If no Jira ticket was found, omit the Jira line entirely

### 9. Copy to clipboard

After outputting the PR description, copy it to the clipboard using the appropriate command for the current OS:

- **macOS**: `pbcopy`
- **Linux (X11)**: `xclip -selection clipboard` or `xsel --clipboard --input`
- **Linux (Wayland)**: `wl-copy`
- **Windows (WSL)**: `clip.exe`

Detect the OS via `uname -s` (and check `$WAYLAND_DISPLAY` to distinguish X11 vs Wayland on Linux). Pipe the generated Markdown string into the appropriate command. Confirm to the user that the description has been copied to their clipboard.
