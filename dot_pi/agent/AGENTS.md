# Global preferences

- Use `codemode` as much as possible for tool calls, not just for MCP or parallel work. This applies to ordinary tools such as `bash`, `read`, `write`, `edit`, `grep` and `find`, as well as MCP tools.
  - When a task needs multiple tool calls, group them in `codemode` whenever possible. Run independent calls together with `Promise.allSettled`; chain dependent calls sequentially in the same script when no intermediate reasoning is needed.
  - Avoid separate sequential tool calls when they could be grouped. Split calls when you must inspect a result and reason before deciding the next step, or when higher-priority instructions require it.
  - Check failures and command exit codes, and do not run overlapping writes or other dependent operations in parallel.
- Prefer Rust-based equivalents of Unix core utilities when available:
  - Use `rg` instead of `grep` for searching.
  - Use `fd` instead of `find` for locating files.
  - Use `bat` instead of `cat` for viewing text files.
- Check that a preferred tool is installed before using it, and fall back to the standard Unix utility when it is unavailable or when its semantics are a better fit (for example, scripts requiring strict POSIX portability).
- When a request names multiple distinct tasks in one message, add each as an entry in the `todo` tool right away, even if individually small — track them as separate items regardless of size.
- When current web content or external facts are required, use the official Exa MCP (`web_search_exa`, `web_fetch_exa`, `web_search_advanced_exa`) through `codemode`; discover its tools with `searchTools()` only when web research is actually needed.
- When completing a task requires checking documentation for a tool, library, or language to get it right, use context7 (`ctx7_library` then `ctx7_docs`) rather than relying on memory.
- Before saying a set of changes is done, run diagnostics on what you changed (linting, type checking, formatting) and resolve any issues. Take the commands from the repo (AGENTS.md, README, package.json scripts, Makefile, mise tasks, CI config) rather than guessing. No language server is installed, so these commands are the only check. If you can't find or run them, or an issue can't be fixed, say so instead of calling the work done.
- The agent runs on Pi-Bolt, whose `bash` tool and `!` commands always run bash (`shellPath` points at Homebrew's bash 5), so write commands for those in bash syntax.
- The user's interactive shell is fish. When giving the user commands to run in their own terminal, or writing fish config, functions or scripts, use fish syntax: `set -x VAR val` instead of `export`, `(cmd)` instead of `$(cmd)`, `; and` / `; or` or `&&` / `||`, `for x in ...; ...; end` instead of `do`/`done`, and `if ...; ...; end` instead of `then`/`fi`. To run fish-specific code from the `bash` tool, use `fish -c '...'`.
- Mark AI-assisted Git work with the model that did it, so reviewers can see it was AI-assisted and which model was used.
  - Commits: a global `commit-msg` hook adds the `Co-authored-by:` trailer for you inside Pi sessions (`extensions/git-coauthor/` wires it up; its `pi-coauthor` command, on PATH in Pi, builds the line from `PI_PROVIDER` and `PI_MODEL`). Write a plain commit message. Do not add the trailer by hand, look up the model, read the environment or check the result afterwards: that costs model calls for nothing.
  - Only step in if you commit with `--no-verify`, or the commit output says `warning: no co-author trailer added`. Then commit again (or amend) with `--trailer "$(pi-coauthor)"`. If `pi-coauthor` itself fails because it does not know the provider, ask rather than guess an address.
  - Never put another trailer after the `Co-authored-by:` line: GitHub only recognises co-authors in the last trailer block.
  - Pull request descriptions, and other Git-hosted text you write (issue and PR comments, review replies), should end with a short line such as `AI-assisted: <Model name>`; take the name from the start of `pi-coauthor`'s output (without any `(via Copilot)`). Apply this in the `pr-description` skill's output too.
  - Don't add the trailer to commits you didn't author, and don't rewrite existing history just to add it unless asked.
